# NuSA 0.4.0 — design and planning

Status: exploratory  
Baseline: NuSA 0.3.0  
Planning branch: `docs/0.4.0-planning`

## 1. Baseline

NuSA 0.3.0 establishes a comparatively stable foundation around five public
model families:

- `SpringModel`
- `BarModel`
- `TrussModel`
- `BeamModel`
- `LinearTriangleModel`

The 0.3.0 line also stabilizes:

- explicit public package exports;
- node and element validation;
- model topology invariants;
- assembly and solution invalidation;
- vector-based global solver state;
- nonzero prescribed displacements;
- singular-system handling;
- a symmetric model-level nodal results API;
- applied-load, nodal-force, and reaction semantics;
- common reporting;
- normalized public visualization names;
- the Gmsh + meshio triangle-mesh subsystem;
- executable examples and CI/release validation.

At the start of 0.4.0, `master` and `develop` are identical and the package
version is `0.3.0`.

## 2. Main observation

The strongest remaining API asymmetry is no longer at model or nodal level.
It is at **element-result level**.

The 0.3.0 changelog already identifies broader element-result normalization
as deferred work for 0.4.0.

Current element result access varies substantially by formulation:

| Element | Current result surface |
| --- | --- |
| Spring | `fx` returns the two end forces |
| Bar | `fx` and `sx` return end-value arrays |
| Truss | `f` and `s` return scalar axial force/stress |
| Beam | `fy` and `m` return end shear/moment arrays |
| LinearTriangle | `sx`, `sy`, `sxy`, `ex`, `ey`, `exy`, plus `get_element_stresses()` and `get_element_strains()` |

Reports currently know these model-specific details through separate
`_get_element_results()` implementations. Plotting also reads raw node or
element attributes directly.

By contrast, nodal/global results already have a coherent public contract:

- `applied_loads` / `applied_load(node)`
- `prescribed_displacements` / `prescribed_displacement(node)`
- `displacements` / `displacement(node)`
- `nodal_forces` / `nodal_force(node)`
- `reactions` / `reaction(node)`

This makes element results the natural architectural focus for 0.4.0.

## 3. Proposed version theme

> **NuSA 0.4.0 should make post-processing a first-class, coherent part of
> the public API.**

The version should primarily answer:

1. How does a user obtain element results consistently?
2. Which quantities belong to the model-level result API and which remain
   formulation-specific?
3. How are result availability and invalidation tied to the solve lifecycle?
4. How should reports and plots consume results without duplicating element
   knowledge?
5. Which recovered nodal quantities are primary FEM results and which are
   visualization/post-processing approximations?

## 4. Design principles

### 4.1 Preserve the stabilized solver core

0.4.0 should not redesign assembly or the reduced-system solver unless a
result-API requirement exposes a concrete defect.

The 0.3.0 contracts for topology, loads, constraints, assembly, solution
invalidation, and nodal/global results should be treated as the baseline.

### 4.2 Normalize access without erasing element physics

Different finite elements naturally produce different physical quantities.
A normalized API should provide a common *access pattern*, not force every
element into an artificial identical result vector.

### 4.3 Keep presentation downstream of results

`simple_report()` and plotting helpers should consume the result contract
rather than encode independent knowledge about raw element properties.

### 4.4 Make solve-state semantics explicit

Model-level solved results currently raise before `solve()` and are
invalidated after relevant input changes. Element-level public result access
should have equally clear semantics.

### 4.5 Distinguish primary and recovered results

For `LinearTriangle`, element stress and strain are primary CST quantities.
Current nodal stress/strain properties are obtained by averaging attached
element values. That recovery rule should be documented and deliberately
designed rather than remaining an implicit side effect of `Node`.

## 5. Candidate work blocks

### 0.4-A — Element-result contract study

Goal: specify the semantics before changing implementation.

Tasks:

- inventory the physical results of each public element type;
- distinguish scalar, end, vector, tensor-component, and recovered results;
- define canonical public names;
- decide where the normalized API lives;
- define pre-solve and invalidation behavior;
- specify backwards-compatibility expectations for existing element
  properties and methods;
- write contract tests before implementation.

Primary design alternatives to compare:

1. **Model-owned API** — for example a model-level
   `element_result(element)` / bulk result interface.
2. **Element-owned API** — for example a consistent `results` mapping on
   every element.
3. **Structured result objects** — richer result records/dataclasses.

A model-owned public entry point is currently the leading candidate because
it can enforce solve lifecycle semantics and mirrors the successful 0.3.0
nodal API, while element-specific calculations can remain close to each
element implementation.

### 0.4-B — Normalized element results

Goal: implement the contract selected in 0.4-A.

Expected outcomes:

- consistent result retrieval for all five model families;
- named, physically meaningful components;
- clear behavior before solve;
- result invalidation after input/topology changes;
- copy/read-only semantics where arrays are exposed;
- regression tests against the current numerical results.

The implementation should avoid changing numerical formulations merely to
make their APIs look alike.

### 0.4-C — Reporting through the result API

Goal: remove duplicated result interpretation from report generation.

Tasks:

- make `simple_report()` consume normalized element results;
- retain distinct tables where different element physics requires them;
- preserve the 0.3.0 distinction among applied loads, `K @ u` nodal
  forces, and reactions;
- test report output for every public model family.

### 0.4-D — Linear-triangle post-processing semantics

Goal: make continuum-element post-processing explicit and trustworthy.

Topics to resolve:

- element stress/strain component naming;
- equivalent stress naming and location;
- whether recovered nodal stresses/strains remain simple averages or use a
  deliberately selected weighting/recovery rule;
- whether recovered nodal fields are public numerical results or primarily a
  visualization convenience;
- behavior at boundaries and mixed-connectivity nodes;
- use of normalized results by contour plotting.

This block should not silently change the meaning of existing CST results.

### 0.4-E — Visualization cleanup

Goal: make plotting a consumer of the public result layer.

Candidate work:

- route result plots through normalized accessors;
- validate requested result names explicitly;
- reduce direct dependence on legacy `Node`/element result attributes;
- make deformation scaling behavior consistent;
- add focused regression coverage for plotting semantics;
- keep Matplotlib as the current backend rather than introducing a new
  visualization architecture in this version.

Visualization changes should follow, not drive, the result API design.

### 0.4-F — Documentation, examples, and release acceptance

Goal: demonstrate the new result workflow with real FEM problems.

Tasks:

- update API documentation;
- update Spring, Bar, Truss, Beam, and LinearTriangle examples;
- include at least one compact post-processing example per result family;
- add release-acceptance tests covering equilibrium and representative
  element results;
- document migration guidance if any 0.3.0 result access changes.

## 6. Explicit non-goals for 0.4.0

Unless exploration uncovers a blocking issue, the following should remain out
of scope:

- new finite-element formulations;
- nonlinear analysis;
- dynamics;
- 3D elements;
- a general material/section system;
- model serialization;
- a GUI;
- a major solver rewrite;
- a major mesh architecture rewrite;
- migration from the current Gmsh executable workflow to the Gmsh Python API.

The existing `meshio` + external Gmsh workflow can receive targeted fixes
and documentation improvements, but it should not define the version.

## 7. Specific findings from the 0.3.0 code

### 7.1 Element result naming is inconsistent

The five element types use different naming conventions and shapes for
closely related concepts. This makes generic reporting, inspection, and
future export difficult.

### 7.2 Reports already expose the abstraction boundary

`Model.simple_report()` is generic except for
`_get_element_results()`. Each model subclass currently translates its
element's private/public conventions into a table. This is a good indicator
of where a normalized intermediate result API can remove duplication.

### 7.3 Continuum nodal fields are currently implicit recovery

`Node.sx`, `sy`, `sxy`, `ex`, `ey`, and `exy` average the
corresponding values of attached elements. This is useful for contour plots
but its numerical meaning is currently implicit.

### 7.4 Plotting still contains historical formulation knowledge

`LinearTriangleModel.plot_nodal_result()` and
`plot_element_result()` maintain their own dictionaries of accepted result
names. Truss and beam deformation plotting use formulation-specific scaling
logic. These are good candidates for cleanup only after result semantics are
fixed.

### 7.5 Mesh is comparatively isolated

The mesh subsystem is already separated into `mesh.py` and `_mesh.py`,
uses `meshio` for triangle-mesh reading, and invokes Gmsh explicitly for
geometry-based generation. The 0.3.0 release hardened this path with real
Gmsh CI smoke tests. It can remain peripheral during 0.4.0.

## 8. Proposed acceptance criteria

0.4.0 should not be considered complete until:

- all five public model families expose element results through the selected
  normalized contract;
- result availability and invalidation semantics are tested;
- existing numerical regression tests remain valid;
- reports consume the normalized result layer;
- LinearTriangle stress/strain and nodal-recovery semantics are documented;
- representative plotting paths consume the result API rather than duplicate
  result definitions;
- the full CI matrix remains green;
- examples use only the intended public API.

## 9. Recommended implementation order

1. **0.4-A:** result inventory and API decision.
2. **0.4-B:** contract tests and normalized element result implementation.
3. **0.4-C:** reporting migration.
4. **0.4-D:** continuum post-processing/recovery semantics.
5. **0.4-E:** visualization cleanup.
6. **0.4-F:** documentation, examples, release acceptance.

## 10. First decision to make

Before implementation, construct a compact result matrix for each element
type containing:

- physical quantity;
- mathematical location (element scalar, element end, component, recovered
  node, etc.);
- current NuSA accessor;
- current return shape;
- proposed canonical name;
- proposed public access path.

That matrix should be the working artifact for 0.4-A and should drive the
first contract tests.
