# NuSA 0.4-A — element-result contract study

Status: design proposal  
Baseline: NuSA 0.3.0  
Parent plan: `docs/planning/0.4.0-design.md`

## 1. Purpose

NuSA 0.3.0 normalized model-level nodal results but intentionally deferred
broader element-result normalization. This document inventories the current
element-result surface and proposes a concrete contract for 0.4.0.

The main design requirement is:

> provide one predictable public way to obtain solved element results without
> erasing formulation-specific mechanics.

A second requirement follows from the existing 0.3.0 lifecycle:

> public solved results must not silently remain available before `solve()`
> or after a model input/topology change invalidates the solution.

## 2. Current result inventory

### 2.1 Spring

Current access:

- `element.fx`
- return shape: NumPy array `(2, 1)`
- mathematical meaning: element nodal force vector
  `k_e u_e`
- locations: element ends `i`, `j`

The two entries are equal and opposite for the current two-node spring.

### 2.2 Bar

Current access:

- `element.fx`
  - shape: `(2, 1)`
  - meaning: element nodal force vector `k_e u_e`
- `element.sx`
  - shape: `(2,)`
  - implementation: `k_e (u_e / A)`

Important semantic observation:

`Bar.sx` produces two opposite-signed values. For a uniform two-node axial
bar, the physical axial stress is a single constant scalar (with a chosen
tension/compression sign convention). Therefore the current `sx` behaves
more like signed end action divided by area than a unique material-point
stress.

This should be preserved for compatibility if necessary, but it should not
define the new normalized stress semantics.

### 2.3 Truss

Current access:

- `element.f`
  - shape: scalar
  - meaning: constant axial internal force
- `element.s`
  - shape: scalar
  - meaning: constant axial stress `f / A`

This is already close to a physically natural result representation, but its
names differ from every other element family.

### 2.4 Beam

Current access:

- `element.fy`
  - shape: `(2, 1)`
  - meaning: element end transverse force actions
- `element.m`
  - shape: `(2, 1)`
  - meaning: element end moment actions

These are end actions derived from `k_e u_e`. They are not a generic
continuous beam-result evaluator.

### 2.5 LinearTriangle

Current access:

- scalar properties:
  - `sx`, `sy`, `sxy`
  - `ex`, `ey`, `exy`
- vector methods:
  - `get_element_stresses()` -> shape `(3,)`
  - `get_element_strains()` -> shape `(3,)`

For the constant-strain triangle these stress and strain components are
constant over the element.

Current nodal stress/strain properties do not come directly from the solve.
`Node.sx`, `sy`, `sxy`, `ex`, `ey`, and `exy` are simple
arithmetic averages of the corresponding attached-element values.

## 3. Result matrix

| Element | Physical quantity | Mathematical location | Current accessor | Current shape | Proposed canonical public quantity |
| --- | --- | --- | --- | --- | --- |
| Spring | element nodal force | ends `i,j` | `fx` | `(2,1)` | `force_i`, `force_j` |
| Bar | element nodal force | ends `i,j` | `fx` | `(2,1)` | `force_i`, `force_j` |
| Bar | axial internal force | constant | not explicit | — | `axial_force` |

| Truss | axial stress | constant | `s` | scalar | `axial_stress` |
| Beam | transverse end action | ends `i,j` | `fy` | `(2,1)` | `shear_force_i`, `shear_force_j` |
| Beam | moment end action | ends `i,j` | `m` | `(2,1)` | `bending_moment_i`, `bending_moment_j` |
| LinearTriangle | normal stress x | element constant | `sx` | scalar | `stress_xx` |
| LinearTriangle | normal stress y | element constant | `sy` | scalar | `stress_yy` |
| LinearTriangle | shear stress xy | element constant | `sxy` | scalar | `stress_xy` |

The proposed normalized surface intentionally favors named scalar values.
This avoids exposing arbitrary array shapes as part of the new contract and
makes report/export/plot selection substantially simpler.

## 4. Access-point alternatives

### Alternative A — public `element.results`

Example:

```python
results = element.results
```

Advantages:

- discoverable from the element itself;
- concise;
- calculation stays near the formulation.

Problems:

- an element does not own the model solve lifecycle;
- the same element object can exist before model insertion;
- direct access cannot naturally enforce "solved model only";
- solution invalidation is model state, not element state;
- it would encourage result access that bypasses the already-established
  model-level 0.3.0 result API.

Conclusion: not recommended as the primary public API.

### Alternative B — structured result classes per formulation

Example:

```python
result = model.element_result(element)
result.axial_force
```

with classes such as `TrussResult`, `BeamResult`,
`LinearTriangleResult`, etc.

Advantages:

- strong typing;
- good IDE discoverability;
- formulation-specific documentation can be rich.

Problems:

- adds several new public classes immediately;
- generic reporting/export still needs a common protocol;
- creates more API surface than the current result set requires;
- can prematurely freeze a hierarchy before more element families exist.

Conclusion: attractive later, but probably too heavy for the first normalized
result contract.

### Alternative C — model-owned flat named mapping

Example:

```python
result = model.element_result(element)
result["axial_force"]
```

Advantages:

- matches the 0.3.0 model-owned result philosophy;
- the model can enforce solved-state and membership rules;
- heterogeneous element physics is represented without sparse generic
  classes;
- flat scalar values are easy to report, export, serialize, and plot;
- new quantities can be added without inventing a new result-class hierarchy.

Problems:

- less IDE discoverability than typed result objects;
- key names become part of the public contract and therefore require care.

Conclusion: recommended for 0.4.0.

## 5. Recommended public contract

### 5.1 Singular access

Add:

```python
model.element_result(element)
```

Behavior:

- accepts only an element that belongs to the model;
- raises before `solve()`;
- raises after any input/topology change that invalidates the solution;
- returns a fresh `dict[str, float]`;
- uses canonical names defined by the element formulation;
- values are scalar numeric results, preferably normalized to Python
  `float` at the public boundary.

Examples:

```python
# Truss
{
    "axial_force": 1250.0,
    "axial_stress": 2.5e6,
}

# Beam
{
    "shear_force_i": 500.0,
    "shear_force_j": -500.0,
    "bending_moment_i": 750.0,
    "bending_moment_j": 250.0,
}

# LinearTriangle
{
    "stress_xx": 2.0e7,
    "stress_yy": 6.0e6,
    "stress_xy": 0.0,
    "strain_xx": 9.1e-5,
    "strain_yy": 0.0,
    "strain_xy": 0.0,
}
```

The exact numerical sign convention remains formulation-defined and must be
documented and regression-tested.

### 5.2 Bulk access

Add:

```python
model.element_results
```

Proposed semantics:

- solved-state requirement identical to `element_result()`;
- returns a tuple in the same insertion order as `model.elements`;
- each tuple entry is a fresh result mapping for the corresponding element.

Example:

```python
for element, result in zip(model.elements, model.element_results):
    ...
```

A tuple is preferred over a dictionary keyed by element objects because it
preserves the model's explicit ordering and avoids making element
hashability/identity part of the public serialization story.

### 5.3 Internal ownership

Recommended split of responsibilities:

- **Model owns public access and lifecycle validation.**
- **Element subclass owns formulation-specific computation.**

Conceptually:

```python
class Model:
    def element_result(self, element):
        self._require_solution()
        self._require_element_membership(element)
        return dict(element._result_values())


class Truss(Element):
    def _result_values(self):
        return {
            "axial_force": float(self.f),
            "axial_stress": float(self.s),
        }
```

The private hook name is illustrative; it is not yet an API decision.

This split keeps mechanics near the element while avoiding a public
`element.results` property that can bypass model lifecycle semantics.

## 6. Proposed canonical quantities by formulation

### Spring

Recommended initial mapping:

```python
{
    "force_i": ...,
    "force_j": ...,
}
```

Open question for implementation study: whether to additionally expose one
signed scalar `spring_force`. The end-action pair is already unambiguous
and matches the current numerical result.

### Bar

Recommended mapping:

```python
{
    "force_i": ...,
    "force_j": ...,
    "axial_force": ...,
    "axial_stress": ...,
}
```

Here `axial_force` and `axial_stress` should be single physical values
with a documented positive-tension convention. They should not simply copy
the current two-entry `sx`.

This block therefore needs a dedicated regression test proving the chosen
sign convention.

### Truss

Recommended mapping:

```python
{
    "axial_force": ...,
    "axial_stress": ...,
}
```

These can initially map directly to the existing scalar mechanics.

### Beam

Recommended mapping:

```python
{
    "shear_force_i": ...,
    "shear_force_j": ...,
    "bending_moment_i": ...,
    "bending_moment_j": ...,
}
```

The `i/j` suffix is intentional: the current quantities are element end
actions. A future beam field evaluator should be a separate API rather than
pretending these are location-independent scalars.

### LinearTriangle

Recommended mapping:

```python
{
    "stress_xx": ...,
    "stress_yy": ...,
    "stress_xy": ...,
    "strain_xx": ...,
    "strain_yy": ...,
    "strain_xy": ...,
}
```

A future `von_mises_stress` quantity is reasonable, but it should be added
deliberately in the continuum post-processing block rather than silently
bundled into the first contract.

## 7. Compatibility strategy

For 0.4.0, keep existing element result properties/methods working unless a
concrete defect requires otherwise:

- `Spring.fx`
- `Bar.fx`, `Bar.sx`
- `Truss.f`, `Truss.s`
- `Beam.fy`, `Beam.m`
- `LinearTriangle.sx/sy/sxy/ex/ey/exy`
- `LinearTriangle.get_element_stresses()`
- `LinearTriangle.get_element_strains()`

The normalized model-owned API becomes the documented preferred path.

This avoids turning 0.4.0 into an unnecessary compatibility break while
still giving NuSA a coherent forward-facing interface.

## 8. Lifecycle contract

The 0.3.0 model already uses solved-result presence as part of its lifecycle.
`_invalidate_solution()` removes solved force/reaction state and resets
nodal solved values while preserving explicit loads and constraints.

The new element result API should follow the same lifecycle:

1. Before `solve()`: unavailable.
2. After `solve()`: available.
3. After load/constraint change: unavailable until solving again.
4. After topology change: unavailable until reassembly/solve.
5. After re-solve: recomputed from current nodal solution.

Element results do not need a separate persistent cache in the first
implementation. Computing them from the current solved displacements keeps
one source of truth and avoids another invalidation layer.

## 9. Contract tests proposed for 0.4-B

The first implementation tests should cover:

- `element_result()` raises before solve;
- foreign/non-member elements are rejected;
- all five public model families return the expected canonical keys;
- all public result values are scalar finite numbers for valid solved
  reference problems;
- `element_results` follows `model.elements` insertion order;
- changing a returned dictionary does not mutate later result retrieval;
- load changes invalidate element results;
- constraint changes invalidate element results;
- topology changes invalidate element results;
- re-solving restores valid results;
- Bar scalar axial force/stress sign convention has an explicit analytical
  regression;
- Truss axial force/stress preserve current validated results;
- Beam end-action signs preserve current validated mechanics;
- LinearTriangle stress/strain values preserve current numerical regression
  results.

## 10. Reporting implication

Once this contract exists, `simple_report()` can stop depending on five
independent result implementations.

A generic report path can iterate:

```python
for element, result in zip(model.elements, model.element_results):
    ...
```

The report may still format different element families differently, but the
source of numerical truth becomes the public normalized result API.

## 11. Visualization implication

Plotting should consume canonical names such as:

- `axial_force`
- `axial_stress`
- `stress_xx`
- `stress_yy`
- `stress_xy`
- `strain_xx`
- `strain_yy`
- `strain_xy`

This removes the need for plotting code to know legacy aliases such as
`f`, `s`, `sx`, or `ex`.

Recovered nodal continuum fields remain a separate design problem for
0.4-D.

## 12. Decision proposed for closing 0.4-A

Adopt the following architecture for the first 0.4.0 implementation:

1. Public result ownership remains at model level.
2. Add `model.element_result(element)`.
3. Add ordered bulk property `model.element_results`.
4. Public result records are flat mappings of canonical scalar names.
5. Formulation-specific calculations remain private to element subclasses.
6. Existing direct element result attributes remain compatible in 0.4.0.
7. Do not cache a second result state initially.
8. Treat Bar physical axial stress semantics explicitly instead of
   normalizing the legacy two-entry `sx` blindly.
9. Defer recovered nodal stress/strain API to 0.4-D.
10. Defer typed result classes until real complexity justifies them.

If accepted, the next branch should implement only the lifecycle/access
skeleton and contract tests first, before migrating reports or plots.
