# NuSA 0.4.0 — target architecture

Status: architecture proposal  
Context: architectural redesign after the 0.3.0 stabilization release

## 1. Motivation

NuSA 0.3.0 intentionally stabilized the historical API and solver behavior.
The next development phase should optimize for a coherent finite-element
software architecture, even when that requires breaking parts of the 0.3.0
public API.

The principal architectural problem in the current design is that the same
objects simultaneously represent:

- finite-element model definition;
- numerical analysis state;
- solved state;
- post-processing state;
- presentation concerns.

Examples include solved displacements and forces stored directly on
`Node`, element results computed by reading those mutable nodal values, and
reporting/plotting methods owned by model classes.

The 0.4.0 architecture should separate these responsibilities while keeping
NuSA small and pleasant to use.

## 2. Design goals

The target architecture should satisfy the following principles.

### 2.1 Model definition is not a solution

A `Model` describes the finite-element problem. Solving it should produce a
separate result object rather than transform the model into the current
solution.

### 2.2 Element formulations are solution-stateless

An element may depend on geometry and properties, but should not read solved
values such as `node.ux` or store solved stresses/forces internally.

Element calculations that depend on the solution should receive the relevant
element displacement vector explicitly.

### 2.3 Analysis orchestration is separate from linear algebra

A finite-element analysis performs validation, DOF mapping, assembly,
boundary-condition treatment, linear solution, reconstruction, reactions,
and element-result evaluation.

The object responsible for this orchestration should be an analysis object,
not a low-level linear-system solver.

### 2.4 Results are stable snapshots

A result represents one completed analysis. Subsequent edits to the model
must not silently change previously computed results.

### 2.5 Post-processing consumes results

Stress recovery, derived quantities, reporting, plotting, and export should
operate on a result rather than on mutable solved state stored in the model.

### 2.6 Easy use remains a first-class requirement

Architectural rigor must not require a ceremonial API. A basic analysis
should still be expressible as:

```python
model = TrussModel(...)
...
result = solve(model)

print(result.displacements)
```

The top-level convenience API may delegate to a richer internal architecture.

## 3. Proposed end-to-end pipeline

The complete NuSA workflow is divided into five conceptual stages:

```text
PREPROCESSING
    Geometry / mesh creation or import
            |
            v
MODEL DEFINITION
    Nodes + elements + properties + loads + constraints
            |
            v
ANALYSIS
    Validation -> DOF map -> assembly -> BC treatment -> linear solve
            |
            v
PRIMARY RESULT
    Displacements + nodal forces + reactions + element results
            |
            v
POSTPROCESSING
    Field extraction -> recovery -> derived quantities
            |
            v
PRESENTATION / EXPORT
    Reports + plots + files
```

Only some of these stages need public classes in 0.4.0.

## 4. Public architecture proposed for 0.4.0

The minimal public architecture should be:

```text
Model
  |
  v
LinearStaticAnalysis
  |
  v
StaticResult
```

with optional preprocessing and post-processing helpers around them.

### 4.1 Model

Responsibility:

> describe one finite-element analysis problem.

For 0.4.0 this includes:

- nodes;
- elements;
- geometry/connectivity;
- material/section parameters currently stored by elements;
- applied nodal loads;
- prescribed nodal displacements / constraints.

It explicitly does **not** contain:

- assembled global matrices as persistent public state;
- solved displacement values;
- solved nodal forces;
- reactions;
- element stresses or internal forces;
- recovered fields;
- plots or reports.

A model may still maintain internal revision counters or cached structural
metadata, but these are implementation details.

### 4.2 Node

A node should become a geometry/topology entity.

Target responsibilities:

- coordinates;
- stable model label/identifier;
- optional future metadata.

Solved attributes should leave `Node`:

- `ux`, `uy`, `ur`;
- `fx`, `fy`, `m`;
- `sx`, `sy`, `sxy`;
- `ex`, `ey`, `exy`;
- `seqv`.

The element-incidence list currently used for nodal stress averaging should
also cease to be a post-processing mechanism.

### 4.3 Element

An element owns its finite-element formulation, geometry reference, and
physical parameters.

Typical element responsibilities:

```python
element.stiffness_matrix()
element.dof_names
element.nodes
```

Solution-dependent calculations should receive local solved state explicitly:

```python
element.compute_results(u_e)
```

For example:

```python
results = truss.compute_results(u_e)
# {
#     "axial_force": ...,
#     "axial_stress": ...,
# }
```

A `LinearTriangle` should conceptually provide:

```python
element.compute_strain(u_e)
element.compute_stress(u_e)
element.compute_results(u_e)
```

rather than reading `node.ux` and `node.uy`.

The exact public/private status of these lower-level methods can remain
narrow in 0.4.0. The architectural requirement is explicit data flow.

## 5. Analysis layer

### 5.1 Why `Analysis` rather than `Solver`

A finite-element static analysis performs more than solving `A x = b`.
It must:

1. validate model compatibility;
2. build the global degree-of-freedom map;
3. assemble the stiffness matrix;
4. assemble load and prescribed-displacement vectors;
5. apply boundary conditions / partition the system;
6. solve the reduced linear system;
7. reconstruct the complete displacement vector;
8. calculate generalized nodal forces and reactions;
9. calculate primary element results;
10. construct a stable result object.

Therefore the high-level public object should be:

```python
LinearStaticAnalysis
```

rather than `LinearStaticSolver`.

### 5.2 Proposed public use

Explicit form:

```python
analysis = LinearStaticAnalysis()
result = analysis.solve(model)
```

Convenience form:

```python
result = nusa.solve(model)
```

where `nusa.solve()` delegates to the default linear-static analysis.

The convenience function should be the preferred beginner-facing API. The
analysis class remains available for configuration and extension.

### 5.3 Analysis object mutability

The default analysis object should preferably be reusable and contain
configuration rather than problem-specific solved state.

For example:

```python
analysis = LinearStaticAnalysis()

r1 = analysis.solve(model_a)
r2 = analysis.solve(model_b)
```

Analysis state created during a solve should be local to that execution or
captured into the returned result.

## 6. Internal analysis stages

The following concepts are architecturally useful, but should remain internal
in 0.4.0 unless a concrete extension requires exposing them.

### 6.1 DOF map

An internal `DofMap` should own the mapping:

```text
(node, dof-name) <-> global integer index
```

This removes solver indexing responsibilities from `Node` labels and from
ad-hoc model methods.

It should also support extraction of element DOF indices.

### 6.2 Assembler

An internal assembler should transform element formulations plus the DOF map
into the global finite-element system.

Conceptually:

```python
system = assemble(model, dof_map)
```

The assembler should not mutate model, nodes, or elements with solved state.

### 6.3 Linear system

A lightweight internal value object may contain:

- global stiffness matrix `K`;
- applied load vector `f`;
- prescribed displacement vector `u_prescribed`;
- free/prescribed DOF indices;
- reduced matrix and right-hand side when useful.

This object is an implementation artifact of an analysis, not part of the
domain model.

### 6.4 Linear algebra solver

The lowest numerical layer should solve a linear system and know nothing
about finite elements.

Conceptually:

```python
u_free = linear_solver.solve(K_reduced, rhs)
```

The initial backend may simply wrap `numpy.linalg.solve`.

A public solver abstraction should be deferred until there is a real second
backend or configuration need. Internally, however, the separation should
exist so sparse solvers can later be introduced without redesigning the FEA
API.

## 7. Validation

Validation should be divided by responsibility.

### 7.1 Model-level validation

Model/domain invariants include:

- valid node coordinates;
- element geometry;
- valid properties;
- element nodes belong to the model;
- duplicate labels;
- unsupported element/model combinations;
- disconnected/orphan nodes when prohibited.

These may be checked incrementally and/or through an explicit internal
validation pass.

### 7.2 Analysis-level validation

Analysis-specific validation includes:

- required DOFs exist;
- applied loads match active DOFs;
- constraints match active DOFs;
- model contains analysable elements;
- supported element formulations for the requested analysis.

A singular system remains a numerical/physical solve failure and should
produce a clear analysis error.

A rich public `ValidationReport` object is not required for 0.4.0. Clear
exceptions are sufficient initially.

## 8. StaticResult

### 8.1 Responsibility

`StaticResult` represents one completed linear-static analysis.

It should own the primary numerical outputs:

- global displacement vector;
- generalized nodal-force vector;
- reaction vector;
- primary element-result records;
- DOF/index metadata required for lookup;
- analysis metadata;
- a stable geometry/connectivity snapshot sufficient for post-processing and
  visualization.

### 8.2 Immutability

Result numerical arrays should be immutable from the public perspective.

At minimum:

- return copies or read-only arrays;
- result records should not expose mutable internal dictionaries directly.

A result must remain valid after:

```python
result = solve(model)
model.add_force(...)
```

The old `result` continues to represent the analysis that produced it.

### 8.3 Snapshot semantics

A result should not recompute primary values by consulting the current
mutable model.

At solve time NuSA should capture enough information to make result
interpretation stable:

- node ordering and labels;
- element ordering and labels;
- node coordinates;
- element connectivity;
- element type/result metadata;
- solved vectors;
- element result values.

For ergonomic access, a result may additionally retain identity maps from
the original `Node` and `Element` objects to the frozen result indices.
The numerical truth, however, must live in the result snapshot.

### 8.4 Proposed public API

```python
result.displacements
result.nodal_forces
result.reactions
result.element_results

result.displacement(node)
result.nodal_force(node)
result.reaction(node)
result.element_result(element)
```

This intentionally relocates the 0.3/early-0.4 result vocabulary from
`Model` to `StaticResult`.

## 9. Element-result ownership

The canonical result names established during 0.4-A/B remain useful:

- `force_i`, `force_j`;
- `axial_force`, `axial_stress`;
- `shear_force_i`, `shear_force_j`;
- `bending_moment_i`, `bending_moment_j`;
- `stress_xx`, `stress_yy`, `stress_xy`;
- `strain_xx`, `strain_yy`, `strain_xy`.

The ownership changes:

```text
early 0.4 proposal:
    model.element_result(element)

target architecture:
    result.element_result(element)
```

Element formulations compute these values from `u_e`; `StaticResult`
stores their frozen values.

## 10. Post-processing architecture

Post-processing should distinguish **primary results** from **derived or
recovered fields**.

### 10.1 Primary fields

Primary solved or directly element-computed data include:

- nodal displacements;
- nodal generalized forces;
- reactions;
- axial force/stress for axial elements;
- beam end actions;
- CST stress and strain.

These belong in `StaticResult`.

### 10.2 Derived quantities

Quantities computed algebraically from primary results include, for example:

- displacement magnitude;
- von Mises stress;
- principal stresses;
- principal strains.

These should be post-processing operations rather than state stored on
`Node`.

### 10.3 Recovery

For continuum elements, converting element-centered quantities into nodal
fields is a distinct post-processing operation.

Target API:

```python
result.nodal_field("stress_xx")
```

For 0.4.0 the default CST recovery may remain arithmetic averaging of
incident element values, but the API should preserve the concept of a
recovery method:

```python
result.nodal_field("stress_xx", recovery="average")
```

Future methods can include area weighting or more sophisticated recovery
without changing where the operation lives.

### 10.4 Field abstraction

A dedicated public `Field` class is **not required initially**.

For 0.4.0:

```python
result.nodal_field("stress_xx")
```

may return a NumPy array ordered consistently with the result's node
snapshot.

Likewise:

```python
result.element_field("stress_xx")
```

may return an array aligned with result element ordering where the quantity
is defined.

Internally, field metadata should be kept structured enough that a future
`Field` object can be introduced without rewriting recovery/visualization.

## 11. Presentation and export

Reporting and visualization are consumers of results; they should not own
FEA mechanics.

### 11.1 Reporting

Preferred architecture:

```python
report(result)
```

or:

```python
result.report()
```

If `result.report()` exists, it should be a convenience delegate to a
reporting module rather than large formatting logic embedded in the result
class.

The current `model.simple_report()` should therefore be considered
transitional.

### 11.2 Visualization

Plotting should consume frozen result geometry and fields:

```python
plot_model(model)
plot_deformed_shape(result)
plot_nodal_field(result, "stress_xx")
plot_element_field(result, "stress_xx")
```

Convenience methods such as:

```python
result.plot_deformed_shape()
```

are acceptable if they simply delegate to `nusa.visualization`.

The visualization module should never discover stresses by reading
`node.sx` or `element.sx`.

### 11.3 Export

A future export layer can consume the same result snapshot:

- CSV/tabular export;
- VTK/mesh formats;
- JSON-like metadata;
- report files.

No general result serialization format is required for 0.4.0, but the
architecture should not prevent it.

## 12. Preprocessing architecture

Preprocessing should remain separate from the analysis/result core.

### 12.1 Geometry

The current `Modeler` combines geometry construction, meshing, and mesh
visualization.

Longer term, the responsibilities are conceptually:

```text
Geometry
   |
   v
Mesher
   |
   v
Mesh
   |
   v
FE Model
```

NuSA does not need to make all four public abstractions immediately.

### 12.2 Mesh

A lightweight `Mesh` value object is a useful architectural boundary and
is recommended when the mesh subsystem is next redesigned.

It should represent, at minimum:

- point coordinates;
- cell connectivity;
- cell type;
- optional physical/group metadata.

Gmsh and meshio should be adapters that produce/consume `Mesh`, not define
the FEA model itself.

### 12.3 Model construction from a mesh

Continuum-model construction should eventually have an explicit conversion
step such as:

```python
mesh = mesher.generate(...)
model = LinearTriangleModel.from_mesh(mesh, E=..., nu=..., t=...)
```

or a dedicated builder function.

This boundary makes it possible to replace Gmsh or import meshes from other
sources without coupling the solver architecture to the mesher.

### 12.4 Scope for 0.4.0

A complete Geometry/Mesher/Mesh rewrite is not required for the core 0.4.0
analysis redesign.

However:

- the analysis core must not depend on `Modeler`;
- future mesh work should target a `Mesh` value boundary;
- current Gmsh + meshio behavior can remain temporarily isolated.

## 13. Loads, constraints, and future LoadCase

A mature FEA system often separates structural topology from load cases.

Possible future architecture:

```text
Model
  +-- nodes
  +-- elements
  +-- properties

LoadCase
  +-- loads
  +-- prescribed displacements

LinearStaticAnalysis.solve(model, load_case)
```

This is architecturally attractive because multiple load cases can share one
structural model.

However, introducing `LoadCase` in 0.4.0 would add user-facing ceremony
before NuSA has actual load-case or load-combination support.

### Decision proposed for 0.4.0

Keep loads and constraints on `Model` as **problem-definition inputs**, but:

- do not store solved state there;
- keep their internal representation separable;
- avoid analysis code that assumes loads must permanently live on the model;
- design `LinearStaticAnalysis` so a future `LoadCase` can supply the same
  input vectors without changing the result architecture.

Introduce `LoadCase` when multiple cases/combinations become a real
feature rather than as speculative infrastructure.

## 14. Material and section abstractions

The same argument applies to `Material` and `Section`.

Today element constructors directly receive values such as `E`, `A`,
`I`, `nu`, and `t`.

Dedicated material/section objects can become valuable when:

- many elements share properties;
- materials need names/metadata;
- section types become richer;
- nonlinear constitutive behavior appears.

They are not required to achieve the core 0.4.0 architecture and should not
delay the Model/Analysis/Result separation.

Element constructors may remain simple for now.

## 15. Proposed module boundaries

NuSA is still small enough that a deep package hierarchy would be premature.

A reasonable 0.4.x target is:

```text
nusa/
    __init__.py
    model.py
    element.py
    analysis.py
    result.py
    post.py
    mesh.py
    visualization.py
    reporting.py
```

Possible responsibilities:

- `model.py`: Model and Node/domain definition;
- `element.py`: Element base + formulations;
- `analysis.py`: LinearStaticAnalysis + private assembly/system helpers;
- `result.py`: StaticResult + frozen result/snapshot structures;
- `post.py`: recovery and derived-field operations;
- `mesh.py`: preprocessing/meshing boundary;
- `visualization.py`: plotting consumers;
- `reporting.py`: report consumers.

The existing `core.py` can be reduced or removed as responsibilities are
migrated. Module splitting should follow responsibility boundaries rather
than file-size goals.

## 16. Suggested public API

A basic spring/truss/bar example should eventually look like:

```python
from nusa import Node, Truss, TrussModel, solve

model = TrussModel("Example")

n1 = Node((0.0, 0.0))
n2 = Node((1.0, 0.0))

model.add_nodes([n1, n2])
model.add_element(Truss((n1, n2), E=200e9, A=1e-4))

model.add_constraint(n1, ux=0.0, uy=0.0)
model.add_constraint(n2, uy=0.0)
model.add_force(n2, (1000.0, 0.0))

result = solve(model)

print(result.displacement(n2))
print(result.reaction(n1))
print(result.element_result(model.elements[0]))
```

The explicit equivalent is:

```python
analysis = LinearStaticAnalysis()
result = analysis.solve(model)
```

For CST post-processing:

```python
result = solve(model)

element_sxx = result.element_field("stress_xx")
nodal_sxx = result.nodal_field("stress_xx")
von_mises = result.nodal_field("von_mises_stress")
```

## 17. Migration from the current architecture

The redesign should be done in vertical increments rather than one large
rewrite.

### Phase A — architecture contracts

Add tests that define:

- model remains free of solved state after analysis;
- `solve(model)` returns `StaticResult`;
- result arrays are stable and independent;
- element computations receive explicit `u_e`;
- editing a model after solve does not mutate an existing result.

### Phase B — StaticResult and analysis orchestration

Move current shared assembly/partition/solve logic out of model subclasses
into `LinearStaticAnalysis`.

Construct `StaticResult` from the existing proven numerical algorithms.

### Phase C — remove solved Node state

Stop writing solution vectors back to `Node`.

Migrate numerical element result calculations to explicit local displacement
vectors.

Remove/deprecate solved node properties from the new 0.4 API.

### Phase D — relocate element-result API

Move:

```python
model.element_result(...)
model.element_results
```

to:

```python
result.element_result(...)
result.element_results
```

Reuse the canonical semantics established in 0.4-B.

### Phase E — post-processing/recovery

Implement explicit element and nodal fields on `StaticResult`.

Remove nodal stress/strain averaging from `Node`.

### Phase F — presentation migration

Move reporting and plotting to consume `StaticResult`.

The generic canonical result-column work from 0.4-C can be reused in the
reporting layer.

### Phase G — cleanup

Remove obsolete model solution invalidation machinery, solved-state
properties, and formulation code that depends on side effects.

Update examples and migration documentation.

## 18. Revised 0.4.0 scope

The architecture pivot makes the earlier 0.4-D/E roadmap subordinate to the
larger redesign.

Recommended 0.4.0 core scope:

1. formalize Model / Analysis / Result responsibilities;
2. implement `LinearStaticAnalysis`;
3. implement immutable/stable `StaticResult`;
4. make elements solution-stateless;
5. remove solved state from `Node`;
6. relocate normalized element results to `StaticResult`;
7. implement explicit continuum field recovery;
8. route reporting through `StaticResult`;
9. route plotting through model/result inputs rather than solved model state;
10. update examples and migration documentation.

Optional if time permits:

- introduce a lightweight `Mesh` value object.

Deferred unless implementation proves them necessary:

- public `LoadCase`;
- public linear-solver hierarchy;
- sparse solver backend;
- Material/Section classes;
- general result serialization;
- nonlinear/transient/modal analyses.

## 19. Architectural acceptance criteria for 0.4.0

0.4.0 should satisfy all of the following before release:

- solving does not store solution state on nodes;
- solving does not require result-bearing element properties;
- one model can be solved repeatedly while earlier results remain unchanged;
- `StaticResult` owns displacements, reactions, nodal forces, and element
  results;
- element result computations use explicit element displacement vectors;
- CST recovered nodal fields are explicit post-processing operations;
- reports use results rather than model solution state;
- plots use model definition and/or result snapshots rather than hidden node
  state;
- analysis orchestration is not duplicated across model subclasses;
- the default beginner workflow remains concise;
- all existing reference problems continue to match their validated numerical
  solutions.

## 20. Core architectural decision

The recommended NuSA direction is:

> **Model defines the finite-element problem; Analysis transforms that
> problem into a stable Result; post-processing and presentation consume the
> Result.**

Everything else should be evaluated against that data-flow rule.
