# NuSA 0.4.0 — LinearStaticAnalysis and StaticResult contract

Status: detailed design proposal  
Parent: `docs/planning/0.4.0-architecture.md`

## 1. Purpose

This document turns the 0.4.0 target architecture into concrete contracts for
the first public analysis and result types:

- `LinearStaticAnalysis`;
- `StaticResult`;
- top-level convenience function `solve(model)`.

The design deliberately keeps lower-level assembly and linear-algebra
machinery internal until multiple backends or analysis types justify a larger
public API.

## 2. Core data-flow contract

The public data flow is:

```text
Model
  |
  |  definition only
  v
LinearStaticAnalysis.solve(model)
  |
  |  validates, assembles, solves, evaluates element response
  v
StaticResult
  |
  |  immutable/stable numerical snapshot
  v
post-processing / reporting / visualization / export
```

The fundamental invariant is:

> A successful analysis does not write solved state back into the model,
> nodes, or elements.

## 3. Beginner-facing API

The preferred simple API is:

```python
from nusa import solve

result = solve(model)
```

For 0.4.0, `solve(model)` means linear static analysis and is equivalent to:

```python
from nusa import LinearStaticAnalysis

result = LinearStaticAnalysis().solve(model)
```

This preserves NuSA's low-friction usage while making the underlying
architecture explicit and extensible.

## 4. LinearStaticAnalysis

### 4.1 Public responsibility

`LinearStaticAnalysis` orchestrates a complete small-displacement,
linear-static finite-element analysis.

It owns the algorithmic workflow, not the finite-element problem definition
and not the persistent result state.

### 4.2 Initial public constructor

Recommended initial signature:

```python
analysis = LinearStaticAnalysis()
```

No public constructor options are required in the first implementation.

Rationale:

- NuSA currently has only one dense direct backend;
- a public solver-strategy hierarchy would be speculative;
- rank checks, partitioning, and NumPy solve behavior are implementation
  details for now;
- adding configuration later is easier than removing prematurely exposed
  options.

Internally the class may accept private/test-only collaborators while the
public constructor remains simple.

### 4.3 Public solve method

Recommended signature:

```python
result = analysis.solve(model)
```

Contract:

- accepts a supported NuSA `Model`;
- validates topology and analysis compatibility;
- reads model definition without storing solved state into it;
- assembles a fresh analysis system;
- applies prescribed displacements;
- solves the free DOFs;
- reconstructs the complete displacement vector;
- computes generalized nodal forces and reactions;
- computes primary element result mappings from explicit element-local
  displacement vectors;
- returns a complete `StaticResult`;
- raises a clear exception if no valid result can be produced.

### 4.4 No partial successful result

For linear static analysis, the public contract should be binary:

```text
success -> valid StaticResult
failure -> exception
```

There is no useful public `converged=False` result for the current direct
linear solve.

This avoids result objects whose fields may or may not be meaningful.

Future nonlinear analyses can define richer convergence/result semantics
without forcing them into `StaticResult`.

### 4.5 Reusability

The analysis object should not retain model-specific solved state:

```python
analysis = LinearStaticAnalysis()

r1 = analysis.solve(model_a)
r2 = analysis.solve(model_b)
```

Both results remain valid and independent.

## 5. Analysis execution pipeline

One call to `solve(model)` should conceptually execute:

```text
1. validate model
2. capture analysis input snapshot
3. construct DOF map
4. assemble K
5. construct applied-load vector f
6. construct prescribed-displacement vector u_p
7. partition free/prescribed DOFs
8. build reduced system
9. validate reduced system / detect singularity
10. solve free DOFs
11. reconstruct full u
12. compute generalized nodal force K @ u
13. compute support reactions
14. compute each element's primary result from u_e
15. build StaticResult
```

No stage needs to mutate the model's solved state.

## 6. Internal collaborators

These are architectural seams, not required public classes in 0.4.0.

### 6.1 DofMap

Responsibilities:

- map `(node, dof_name)` to global integer index;
- map a global index back to node/component metadata;
- return element global DOF indices;
- preserve deterministic model node ordering.

Conceptually:

```python
dof_map.index(node, "ux")
dof_map.element_indices(element)
```

The current dependence on `node.label` for numerical indexing must remain
eliminated; labels are identifiers, not solver positions.

### 6.2 Assembly

The assembly function consumes:

- model topology;
- element stiffness matrices;
- DOF map.

It returns a fresh global stiffness matrix and does not cache it on the
model.

### 6.3 System partition

A private function/value object handles:

- prescribed DOF indices;
- free DOF indices;
- reduced stiffness matrix;
- reduced right-hand side.

The existing non-zero prescribed-displacement logic should be reused
numerically.

### 6.4 Linear solver

The first backend may remain a thin call to `numpy.linalg.solve`.

The FEA analysis layer owns singularity/error translation.

A public `LinearSolver` class is deferred until NuSA has a second backend
or a real solver-configuration use case.

## 7. StaticResult

### 7.1 Meaning

`StaticResult` is a stable snapshot of one successfully completed linear
static analysis.

It is not:

- a mutable continuation of the model;
- a cache whose values are recomputed from current node/element state;
- a general bag of matrices generated during solving.

### 7.2 Construction

Users should not normally instantiate `StaticResult` directly.

Its constructor may be public at the Python level, but its arguments should
be treated as an implementation contract owned by the analysis layer.

The supported user construction path is:

```python
result = solve(model)
```

## 8. Primary numerical data owned by StaticResult

A result should freeze the following arrays from the solved analysis:

### 8.1 Input vectors relevant to the solved problem

```text
applied_loads
prescribed_displacements
```

These belong in the result snapshot because they define the solved load/BC
state and are needed for equilibrium checks, reporting, and reproducibility.

Unprescribed displacement entries may continue to use `NaN` in the
prescribed-displacement vector.

### 8.2 Solved vectors

```text
displacements
nodal_forces
reactions
```

Definitions remain:

- `displacements`: complete solved global displacement vector;
- `nodal_forces`: generalized global vector `K @ u`;
- `reactions`: `K @ u - f` on prescribed DOFs and zero on free DOFs.

### 8.3 Primary element results

Each element receives its explicit local displacement vector `u_e` and
produces canonical scalar result values.

The result freezes these records in element order.

Examples remain:

```python
# Truss
{
    "axial_force": ...,
    "axial_stress": ...,
}

# LinearTriangle
{
    "stress_xx": ...,
    "stress_yy": ...,
    "stress_xy": ...,
    "strain_xx": ...,
    "strain_yy": ...,
    "strain_xy": ...,
}
```

These are evaluated at solve time rather than lazily from the current model.

## 9. Data intentionally not required in StaticResult

The minimal result should not automatically retain every intermediate
analysis matrix.

In particular, 0.4.0 does **not** require public persistent storage of:

- full global stiffness matrix;
- reduced stiffness matrix;
- reduced right-hand side;
- factorization objects;
- temporary assembly buffers.

Reasons:

- they are analysis artifacts rather than physical results;
- retaining a global matrix can substantially increase result memory usage;
- future sparse systems make this distinction more important.

NuSA's educational use may justify an explicit system-inspection API later,
for example an `analysis.assemble(model)` or optional diagnostics object.
That should be designed separately rather than turning every result into a
debug dump.

## 10. Result snapshot metadata

To remain independent from future model edits, `StaticResult` should
capture structural metadata at solve time.

Minimum frozen snapshot:

### Nodes

For every node, in result order:

- original label;
- coordinates.

### Elements

For every element, in result order:

- original label;
- element type;
- connectivity expressed as result node indices.

### DOF metadata

- displacement DOF names;
- force/resultant DOF names;
- global ordering.

### Analysis metadata

At minimum:

- analysis type (linear static);
- model name at solve time.

A model revision number is useful internally if introduced, but result
correctness must not depend on comparing against the current model revision.

## 11. Identity maps and stable snapshots

There are two different concerns:

1. stable numerical storage;
2. ergonomic lookup using the original Python objects.

They should not be confused.

### 11.1 Numerical truth

Numerical result data is indexed using the result's own frozen ordering.

It does not depend on current properties of the original `Node` or
`Element` objects.

### 11.2 Convenience identity maps

The result may retain private maps:

```text
original Node object -> result node index
original Element object -> result element index
```

This permits:

```python
result.displacement(n2)
result.element_result(e1)
```

even though the underlying values come from frozen arrays/records.

If `n2.x`, its label, or the model topology is later changed, the old
result still uses its captured metadata.

### 11.3 Future serialization

Object-identity maps are conveniences and must not become the serialized
identity model.

Future serialization can rely on frozen indices/labels/connectivity.

## 12. Public StaticResult API

### 12.1 Whole-vector properties

Recommended:

```python
result.applied_loads
result.prescribed_displacements

result.displacements
result.nodal_forces
result.reactions
```

All return data that cannot mutate the internal result.

Implementation options:

- copies;
- read-only NumPy arrays.

For the first implementation, returning copies is the safest simple contract.

### 12.2 Per-node access

Recommended:

```python
result.applied_load(node)
result.prescribed_displacement(node)

result.displacement(node)
result.nodal_force(node)
result.reaction(node)
```

Return type:

```python
dict[str, float]
```

Examples:

```python
result.displacement(n2)
# {"ux": 0.0012, "uy": -0.0004}

result.reaction(n1)
# {"fx": -1000.0, "fy": 500.0}
```

This preserves the successful named-component semantics established in
0.3.0 while relocating ownership to the result.

### 12.3 Element results

Recommended:

```python
result.element_result(element)
result.element_results
```

`element_result(element)` returns a fresh mapping:

```python
dict[str, float]
```

`element_results` returns an ordered tuple aligned with the result's
element snapshot.

The canonical names created in 0.4-B remain the contract.

### 12.4 Structural metadata

Recommended read-only inspection:

```python
result.model_name
result.node_labels
result.node_coordinates
result.element_labels
result.connectivity
result.displacement_dofs
result.force_dofs
```

Not all of these need to be prominent top-level documentation, but the
result must expose enough stable geometry/order information for plotting,
export, and inspection without consulting the mutable model.

## 13. Lookup behavior

### 13.1 Accepted node lookup in 0.4.0

Primary convenience path:

```python
result.displacement(original_node_object)
```

Passing a node that did not belong to the solved model raises `ValueError`.

### 13.2 Accepted element lookup

Likewise:

```python
result.element_result(original_element_object)
```

Foreign elements raise `ValueError`.

### 13.3 Label-based lookup

Do not overload the first contract with ambiguous `int | Node` signatures.

If label-based lookup becomes desirable, add explicit methods later:

```python
result.node_by_label(label)
result.element_by_label(label)
```

This keeps lookup semantics unambiguous.

## 14. Element response contract

To remove solution state from elements, solution-dependent formulation
methods must accept an explicit local displacement vector.

Recommended architectural shape:

```python
ke = element.stiffness_matrix()
values = element.compute_results(u_e)
```

The exact public naming can be finalized during implementation, but the
following invariants are mandatory:

- stiffness computation depends only on geometry/properties;
- element result computation depends only on geometry/properties + explicit
  `u_e`;
- no element result method reads `node.ux`, `node.uy`, `node.ur`, or
  solved force attributes;
- no result method writes solved values back to an element.

### Examples

Spring:

```python
def compute_results(self, u_e):
    f_e = self.stiffness_matrix() @ u_e
    return {
        "force_i": float(f_e[0]),
        "force_j": float(f_e[1]),
    }
```

Truss:

```python
def compute_results(self, u_e):
    axial_force = ...
    return {
        "axial_force": float(axial_force),
        "axial_stress": float(axial_force / self.A),
    }
```

Linear triangle:

```python
def compute_strain(self, u_e):
    return self.B @ u_e

def compute_stress(self, u_e):
    return self.D @ self.compute_strain(u_e)
```

The canonical result mapping is built from those explicit calculations.

## 15. Post-processing contract

Post-processing is intentionally downstream from `StaticResult`.

### 15.1 Element field

Recommended:

```python
result.element_field("stress_xx")
```

Returns an array in result element order when the quantity is defined for
the model's elements.

This is a projection of already-frozen primary element records, not a new
FE solve.

### 15.2 Nodal recovery

Recommended:

```python
result.nodal_field("stress_xx")
```

Conceptually this delegates to post-processing logic:

```python
post.recover_nodal_field(result, "stress_xx", method="average")
```

For 0.4.0 the default CST method may be arithmetic averaging.

### 15.3 Derived quantities

Derived quantities should be registered/calculated from primary result
fields, not stored on nodes.

Examples:

```text
displacement_magnitude
von_mises_stress
principal_stress_1
principal_stress_2
```

The exact derived-field set can be introduced incrementally.

### 15.4 Result convenience versus module ownership

A method such as:

```python
result.nodal_field(...)
```

is acceptable as a convenience API, but the implementation should delegate
to `nusa.post`.

This keeps `StaticResult` from becoming the owner of recovery algorithms.

## 16. Reporting contract

Reporting consumes a result snapshot.

Canonical functional API:

```python
text = simple_report(result)
```

Optional convenience:

```python
text = result.simple_report(...)
```

If the convenience method exists, it delegates to `nusa.reporting`.

The generic result-column semantics already implemented in 0.4-C can be
moved rather than discarded.

## 17. Visualization contract

Geometry-only visualization may consume a model:

```python
plot_model(model)
```

Solved visualization consumes a result:

```python
plot_deformed_shape(result)
plot_nodal_field(result, "stress_xx")
plot_element_field(result, "stress_xx")
```

A solved plot must not read current solved values from the original nodes or
elements.

The result's frozen geometry is sufficient for deformed/result plots.

## 18. Error model

The first implementation should prefer a small number of clear exception
types/messages over a deep hierarchy.

### Input/domain errors

Use `TypeError` / `ValueError` for:

- unsupported object types;
- invalid node/element membership;
- invalid properties;
- invalid load/constraint components;
- invalid topology.

### Analysis failure

A singular or otherwise unsolvable linear system should continue to surface
as a clear numerical analysis exception.

A NuSA-specific `AnalysisError` hierarchy can be introduced later if
multiple failure modes justify it.

### Result lookup errors

Foreign node/element access should raise `ValueError`.

Unknown field names should raise `ValueError` with the available canonical
names.

## 19. Model lifecycle after the redesign

Once solved state is removed from `Model`, most current solution
invalidation machinery disappears.

The model still needs ordinary consistency behavior when topology or inputs
change, but it no longer needs to invalidate:

- displacement results;
- reactions;
- nodal-force results;
- element-result caches.

Each call to `solve(model)` consumes the model's current definition and
produces a new independent result.

Example:

```python
r1 = solve(model)

model.add_force(n2, (20.0, 0.0))

r2 = solve(model)

# r1 remains unchanged
# r2 corresponds to the new load state
```

This becomes a core regression test.

## 20. Assembly caching

Do **not** preserve model-owned assembly caching as a public architectural
requirement in the first redesign.

The initial `LinearStaticAnalysis` may assemble fresh for every solve.

Reasons:

- correctness and ownership become simpler;
- no invalidation protocol is required;
- current NuSA problem sizes are small;
- caching can be added later behind the analysis layer using model revision
  information if profiling shows a real need.

This is a deliberate trade: clean ownership first, optimization later.

## 21. Model class hierarchy in 0.4.0

The current `SpringModel`, `BarModel`, `TrussModel`, `BeamModel`,
and `LinearTriangleModel` may remain as convenient problem-definition
classes.

However, their responsibilities should shrink.

They should primarily declare:

- supported element family;
- active displacement DOF names;
- corresponding force/resultant names;
- domain-specific load helpers where useful.

They should no longer implement:

- `assemble()`;
- `solve()`;
- solved-result properties;
- solved plotting;
- solved report generation.

A later version may investigate a more general heterogeneous `Model`, but
that is not necessary for the first architecture correction.

## 22. Result class hierarchy

Do not introduce one result subclass per element type.

One:

```python
StaticResult
```

is sufficient for all current linear-static model families.

Reasons:

- global solved quantities share the same semantics;
- formulation differences already live in canonical element-result records;
- a class hierarchy such as `TrussResult`, `BeamResult`, etc. would mirror
  element types unnecessarily.

Future analysis types may justify siblings:

```text
StaticResult
ModalResult
TransientResult
NonlinearResult
```

That is an analysis-type distinction, which is a more meaningful boundary.

## 23. Proposed internal result layout

Illustrative only:

```python
StaticResult(
    model_name=...,
    node_labels=(...),
    node_coordinates=...,
    element_labels=(...),
    element_types=(...),
    connectivity=(...),
    displacement_dofs=(...),
    force_dofs=(...),
    applied_loads=...,
    prescribed_displacements=...,
    displacements=...,
    nodal_forces=...,
    reactions=...,
    element_results=(..., ...),
    node_identity_map=...,
    element_identity_map=...,
)
```

The private storage may use frozen dataclasses, tuples, and read-only NumPy
arrays.

The public API should not expose these implementation details directly.

## 24. Proposed acceptance tests

### 24.1 Analysis ownership

- `solve(model)` returns `StaticResult`;
- `LinearStaticAnalysis().solve(model)` gives the same numerical result;
- solve does not set solved values on nodes;
- solve does not set solved result state on elements;
- solve does not store solved vectors on model.

### 24.2 Numerical equivalence

For Spring, Bar, Truss, Beam, and LinearTriangle:

- displacement regression matches current validated values;
- nodal-force regression matches current validated values;
- reaction regression matches current validated values;
- element-result regression matches current canonical values.

### 24.3 Stability

- modify loads after solving -> old result unchanged;
- modify constraints after solving -> old result unchanged;
- modify model topology after solving -> old result unchanged;
- solve again -> new result reflects new model definition.

### 24.4 Immutability

- mutating an array returned by a public result property does not mutate the
  result;
- mutating a dictionary returned by `element_result()` does not mutate the
  result.

### 24.5 Lookup

- original node objects resolve to frozen result positions;
- original element objects resolve to frozen result positions;
- foreign nodes/elements are rejected.

### 24.6 Post-processing

- element fields follow frozen element ordering;
- CST constant-field recovery reproduces an affine exact solution;
- nodal recovery never reads current `Node.sx`-style state.

## 25. Recommended implementation sequence

The architecture should be implemented incrementally.

### Step 1 — contract tests and result skeleton

Add:

- `StaticResult`;
- `LinearStaticAnalysis`;
- `solve(model)`;

initially reusing current proven numerical helper logic where practical.

### Step 2 — analysis owns assembly/solution

Move:

- DOF indexing;
- stiffness assembly;
- partitioning;
- linear solve;
- reaction calculation;

out of model subclasses.

### Step 3 — explicit element-local result computation

Introduce `compute_results(u_e)`-style behavior for all five element
families.

At this point the analysis can build complete element-result records without
writing solved state to nodes.

### Step 4 — stop mutating Node/Element solved state

Remove solution write-back from the analysis path.

Make the new result API the source of truth.

### Step 5 — migrate reporting and visualization

Move 0.4-C generic reporting logic to result consumers.

Migrate plotting to model/result functions.

### Step 6 — nodal recovery

Implement explicit continuum post-processing on frozen result fields.

### Step 7 — remove transitional solved-state API

Delete obsolete model/node/element solved-state machinery before 0.4.0 final,
unless a narrowly justified compatibility shim is retained temporarily.

## 26. Decisions proposed for approval

1. Public solve flow is `result = solve(model)`, backed by
   `LinearStaticAnalysis().solve(model)`.
2. `LinearStaticAnalysis` is the public FEA orchestrator; a lower-level
   linear solver remains internal.
3. `StaticResult` is the single result type for all current static element
   families.
4. Results are stable snapshots independent of subsequent model edits.
5. Result snapshots include solved inputs (loads/BCs), geometry/connectivity
   metadata, global solved vectors, and primary element results.
6. Global stiffness/reduced matrices are not mandatory result payload.
7. Node/element object identity is retained only as an ergonomic lookup map;
   frozen indices/metadata are the numerical truth.
8. Element response calculations receive explicit local displacement vectors.
9. Model-owned assembly caching is dropped initially; each solve may assemble
   fresh.
10. Post-processing algorithms live outside `StaticResult`, with
    `result.nodal_field(...)` and similar methods allowed as delegates.
11. Model subclasses remain temporarily as lightweight domain-definition
    conveniences.
12. Result subclasses should follow analysis type, not element type.

If these decisions are accepted, the next implementation branch should add
contract tests and the `StaticResult` / `LinearStaticAnalysis` skeleton
without yet deleting the legacy solve path.
